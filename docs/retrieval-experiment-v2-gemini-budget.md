# Gemini Retrieval 소규모 비교 실험

실행일: 2026-09-04 01:19 KST (`2026-09-03T16:19:07.557224Z`). [원본 결과 JSON](retrieval-experiment-v2-gemini-budget.json).

## 목적과 API 사용 범위

[원본 프로젝트](https://github.com/100bee/rag-ops-copilot)의 Vector·Keyword·Hybrid 비교를 실제 의미 임베딩으로 수행했다. 질문 임베딩을 재사용하고 생성 모델 호출을 생략해 API 사용량을 줄였다.

| 항목 | 실제 사용량 |
| --- | ---: |
| 임베딩할 질문 | 20개, 합계 750자 |
| Gemini 임베딩 HTTP 요청 | `batchEmbedContents` 1회 |
| 문서 재색인 | 0회; 기존 12개 문서 사용 |
| 답변 생성 API 호출 | 0회 |
| 생성 출력 토큰 | 0 |
| 임베딩 입력 토큰 | 이번 실행에서 수집하지 않음 |

실행 중 호출을 계측했으며 배치 1회·질문 20개·750자를 초과하거나 생성 API를 호출하면 중단하도록 제한했다. **750자는 750토큰이라는 뜻이 아니다.** 토큰 수 확인을 위한 추가 API 호출은 하지 않았다. HTTP 요청 1회에도 임베딩 입력 20개가 포함되므로 이를 할당량 1개로 해석하지 않는다. 여러 입력을 한 요청에 보내는 동기 API는 [Google 임베딩 문서](https://ai.google.dev/api/embeddings#method:-models.batchembedcontents)를 따른다.

기존 방식의 1회 비교는 Vector 20개 + Hybrid 20개로 임베딩 입력 40개가 필요했다. 이번에는 질문마다 한 번 생성한 벡터를 두 방식에 공유해 입력량을 절반으로 줄였다. 캐시는 해당 실험 프로세스 안에서만 사용한다.

## 고정 조건

- 기존 문서 12개, 평가 질문 20개: 답변 가능 15개, 거절 대상 5개.
- `gemini-embedding-001`, `RETRIEVAL_QUERY`, 1536차원, 정규화한 벡터.
- 청크 크기 900, 중첩 120, 후보 20개, Top-K 5.
- Hybrid 가중치 Vector 0.72 / Keyword 0.28.
- 검색 방식별 1회 실행. 검색 방식·임계값을 결과에 맞춰 조정하지 않았다.
- 원본 JSON에 데이터셋과 문서 checksum을 기록해 실험에 사용한 자료를 식별한다.
- 검색 근거 판정은 의미 유사도 0.35, 키워드 일치 2개·비율 20% 기준을 사용한다. **생성 모델의 거절이나 답변 사실 정확도는 측정하지 않는다.**

## 결과

| 방식 | Recall@5 | MRR | 전체 근거 판정 일치율 | 거절 대상 거절 성공 | 답변 가능 질문의 잘못된 거절 | 평균 DB 검색·정렬 시간 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Vector | 100.0% | 1.000 | 75.0% | 0/5 | 0/15 | 4.35ms |
| Keyword | 93.3% | 0.817 | 80.0% | 4/5 | 3/15 | 1.75ms |
| Hybrid | 100.0% | 0.878 | 75.0% | 0/5 | 0/15 | 3.95ms |

Recall@5와 MRR은 답변 가능한 15문항으로 계산한다. 복수 정답 문서는 Recall에서 각각 반영한다. 근거 판정 일치율은 답변 가능/거절 대상 전체 20문항으로 계산한다.

20문항의 질문 임베딩 준비에는 **1,430ms**가 별도로 걸렸다. 표의 시간은 임베딩 API 시간을 제외하며 사용자 한 요청의 전체 응답시간이 아니다. 단 한 번의 실행과 작은 DB에서 얻은 수 ms 차이로 일반적인 속도 우위를 주장하지 않는다.

## 확인한 사례

1. **다른 표현의 질문을 의미 검색이 찾았다.** `challenge-02`의 “파일을 올린 뒤 오랫동안 처리 중이라고만 나오고…”에 대해 Vector는 Worker 정체 문서를 1위로 찾았다. Keyword는 놓쳤고, Hybrid는 3위로 찾았다.
2. **키워드 결합이 순위를 낮추기도 했다.** `challenge-01`의 “외부 모델이 호출을 거부해…”는 Vector에서 API 429 문서가 1위였지만 Hybrid에서는 3위였다. `dev-10`의 응답 지연 질문도 1위에서 2위로 밀렸다. 현재 가중치에서 Hybrid가 가장 좋은 방식은 아니었다.
3. **좋은 검색 순위만으로 답변 가능성을 판정할 수 없다.** Vector·Hybrid는 프린터·휴가 질문 및 배당일·피해 금액·관리자 개인정보 질문을 모두 답변 가능으로 잘못 분류했다. 의미 유사도 0.35 기준이 이 모델과 데이터에서 거절 경계로 충분하지 않았다.
4. **Keyword도 실패가 있다.** 피해 금액·보상 승인자 질문을 잘못 허용했고, 근거 부족 정책 및 두 패러프레이즈 질문을 잘못 거절했다.

## 결론과 다음 실험

현재 자동 선택 규칙은 Recall → MRR → 근거 판정 일치율을 우선하므로 **Vector**를 선택했다. 이는 이번 데이터의 검색 순위에 대한 결과이며 완성된 답변 시스템의 추천으로 확장할 수 없다. Vector의 MRR은 1.000이었지만 거절 대상 5개를 모두 허용한 문제는 별도로 해결해야 한다.

다음 개선은 dev 질문에서 유사도·키워드 기준을 검토하고 새로운 검증 질문으로 확인하는 것이다. 이후 필요할 때만 소수의 생성 답변을 직접 출처와 대조한다. 이전 브라우저 확인에서는 피해 금액 질문을 생성 모델이 거절했지만, 그 한 사례를 전체 거절 성능으로 계산하지 않는다. 이번 실험으로 서비스 기본 검색 방식이나 거절 임계값을 변경하지 않았다.

## 재현

Gemini로 색인된 문서가 준비된 환경에서 실행한다. `--seed`를 넣지 않아 문서 임베딩을 추가 생성하지 않는다.

```bash
docker compose exec -T backend python -m app.evaluate --repetitions 1 --reuse-query-embeddings > docs/my-gemini-retrieval.json
```

CLI 결과에는 임베딩 입력 개수·문자 수·준비 시간과 검색시간의 측정 범위가 포함된다. 실행하면 현재 질문마다 임베딩이 다시 생성된다. `api_usage`의 실제 호출 계측 기록은 위 원본 실행에서 별도로 추가한 값이다.

새 재사용 기능은 PostgreSQL 통합 테스트에서 기존 방식과 검색·평가 결과가 같은지, 반복해도 질문을 한 번만 임베딩하는지 확인했다. 전체 테스트 **23개 통과**.
